# 동시 접속이 왜 버벅였고, 무엇을 고쳤나

30명이 한 반에서 동시에 들어오면 v1은 느렸습니다. 원인은 네 가지였고, 전부 고쳤습니다.

---

## 원인 1 — 화면 자체를 Apps Script가 만들어 보냈다

Apps Script의 `HtmlService`는 페이지를 이중 iframe 샌드박스에 넣어 전송합니다.
학생 1명이 접속할 때마다:

```
브라우저 → Apps Script 실행 → HTML 조립 → 샌드박스 래핑 → 전송
```

CSS·폰트·자바스크립트까지 전부 이 경로를 탑니다. 첫 화면이 뜨는 데 **3~6초**.
30명이 동시에 하면 서버 실행이 30개 쌓입니다.

### 고친 방법 — 화면을 GitHub Pages로 옮김

`index.html`, `neon.css`, `api.js` 는 이제 GitHub의 CDN에서 옵니다.
정적 파일이라 **동시 접속 제한이 사실상 없고**, 브라우저 캐시도 정상 작동합니다.

```
브라우저 → GitHub CDN (0.2초, 두 번째부터는 캐시) → 화면 즉시 표시
         → Apps Script 에는 "문항 데이터"만 요청
```

Apps Script가 하는 일이 **HTML 조립 → JSON 몇 KB 전송**으로 줄었습니다.

## 원인 2 — 학생마다 스프레드시트를 통째로 읽었다

v1의 `getQuizForStudent`는 학생이 들어올 때마다 `문제은행` 시트 전체를 읽었습니다.
평가가 쌓일수록 느려지고, 30명이면 30번 읽습니다. 시트 읽기는 1회에 1~2초입니다.

### 고친 방법 — CacheService

```js
function loadQuiz_(quizId) {
  const hit = CacheService.getScriptCache().get('Q_' + quizId);
  if (hit) return JSON.parse(hit);      // ← 30명 중 29명은 여기서 끝
  return cacheQuiz_(quizId);            // ← 시트를 읽는 건 첫 1명뿐
}
```

캐시는 6시간 유지됩니다. 게다가 **저장 버튼을 누르는 순간 미리 캐시에 올려 두므로**,
실제로는 첫 번째 학생도 시트를 읽지 않습니다.

> 시트에서 문항을 직접 고쳤다면 출제실 → 설정 → **🧹 캐시 비우기**

## 원인 3 — 제출 때 잠금을 오래 잡았다

v1은 `LockService`로 잠근 채 **시트를 읽고 → 채점하고 → 두 시트에 썼습니다.**
한 명당 잠금 점유가 3~4초. 30명이면 마지막 학생은 **90초 넘게** 기다립니다.
그동안 "끊겼다"고 느끼고 새로고침하면 상황이 더 나빠집니다.

### 고친 방법 — 잠금 구간을 시트 쓰기 1회로 축소

```js
// 잠금 밖: 캐시에서 정답 가져와 메모리에서 채점 (0.05초)
const q = loadQuiz_(payload.quizId);
... 채점 ...

// 잠금 안: 딱 한 줄 쓰기 (0.3~0.6초)
if (!lock.tryLock(28000)) throw new Error('지금 접속이 몰려 있습니다...');
try { respSheet_().appendRow(row); } finally { lock.releaseLock(); }
```

점유 시간 **3~4초 → 0.3~0.6초**. 30명이 동시에 눌러도 마지막 학생이 약 15초 안에 끝납니다.
실제로는 푸는 속도가 달라 제출이 저절로 분산되므로 체감 대기는 거의 없습니다.

## 원인 4 — '문항응답' 시트에 학생당 10줄을 더 썼다

한 반 30명이면 **300줄**을 추가로 썼습니다. 이게 잠금 시간의 절반을 차지했습니다.

### 고친 방법 — 시트를 없애고 대시보드에서 계산

`응답` 시트에는 이미 `응답JSON`(학생이 고른 답)이 들어 있고,
`문제은행`에는 정답이 있습니다. 둘을 대시보드에서 맞춰 보면
문항별 정답률과 최다 오답이 그대로 나옵니다.

**제출 1건당 시트 쓰기 = 2회 → 1회.** 대시보드 기능은 그대로입니다.

> v1을 쓰던 스프레드시트라면 `setup`을 다시 실행할 때 `문항응답` 시트가 자동 정리됩니다.

## 추가 안전장치 — 그래도 실패하면

학생 쪽 `assets/api.js` 에 세 겹의 보호막을 넣었습니다.

**① 자동 재시도 (지수 백오프)**
실패하면 0.8초 → 1.6초 → 3.2초 간격으로 다시 시도합니다.
학생 화면에는 "접속이 몰려 다시 보내는 중입니다. 창을 닫지 마세요"라고 표시됩니다.

**② POST 실패 시 GET 우회**
학교 방화벽이나 브라우저 설정으로 POST가 막히면,
답안을 base64로 인코딩해 GET으로 다시 보냅니다.

**③ 실수로 나가기 방지**
문제를 푸는 도중 새로고침·뒤로가기를 누르면 브라우저가 확인 창을 띄웁니다.

또 "마감된 평가", "PIN 오류"처럼 **다시 시도해도 소용없는 오류**는 재시도하지 않고
바로 안내 문구를 보여 줍니다. 서버에 불필요한 부하를 주지 않기 위해서입니다.

## 그래도 느리다면 — 수업 운영 요령

Apps Script는 무료 서비스라 **동시 실행 개수에 한도**가 있습니다.
아래 세 가지면 사실상 문제가 생기지 않습니다.

1. **QR을 먼저 띄우고 "다 됐으면 손 드세요"** — 화면 로딩이 자연스럽게 분산됩니다.
   (화면은 CDN에서 오므로 이 단계는 원래 빠릅니다.)
2. **제한시간을 두세요** — 제한시간이 있으면 제출이 마지막 1분에 몰립니다.
   제한시간을 **넉넉히(10분)** 잡거나 무제한으로 두면 오히려 분산됩니다.
3. **두 반을 동시에 시키지 마세요** — 한 반씩이면 30명, 두 반이면 60명이 겹칩니다.

한 학년 전체(200명 이상)를 동시에 봐야 한다면 미리 알려 주세요.
제출 데이터를 잠깐 모았다가 한 번에 쓰는 큐 방식으로 바꿀 수 있습니다.
